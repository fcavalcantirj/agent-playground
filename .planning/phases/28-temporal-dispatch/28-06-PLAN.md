**Step 1 — extend insert_pending to accept idempotency_key (Plan 05 default Option A) and return the row WITH workflow_id slot.**

Plan 05 added an `idempotency_key` column to inapp_messages by default (Option A). Update `insert_pending` to accept an optional `idempotency_key: str | None = None` kwarg and persist it:

```
async def insert_pending(
    conn,
    *,
    agent_id: UUID,
    user_id: UUID,
    content: str,
    idempotency_key: str | None = None,
) -> UUID:
    row = await conn.fetchrow(
        """
        INSERT INTO inapp_messages (agent_id, user_id, content, idempotency_key)
        VALUES ($1, $2, $3, $4)
        ON CONFLICT (user_id, idempotency_key) WHERE idempotency_key IS NOT NULL
            DO UPDATE SET content = inapp_messages.content  -- no-op; gets the existing row
        RETURNING id
        """,
        agent_id, user_id, content, idempotency_key,
    )
    return row["id"]
```

The `ON CONFLICT ... DO UPDATE SET content = inapp_messages.content` is a Postgres idiom for "give me back the existing row's id without changing it" — RETURNING then surfaces the (possibly pre-existing) message_id. This makes the insert idempotent at the DB layer; combined with the unique partial index from Plan 05 Option A, RESEARCH §7 R3 is closed.

If Plan 05's Pre-step inspection found the column already existed in 007 (no op.add_column needed in 011), the unique partial index is still in place — the insert_pending change above is identical either way. Defense-in-depth (Option A column-level + Option B middleware TTL) is achieved.

Add to `inapp_messages_store.py`:

async def set_workflow_id(conn, *, message_id: UUID, workflow_id: str) -> None:
    """Phase 28 — back-fill the workflow_id column for ops correlation.

    Called by the route handler AFTER start_workflow returns. Best-effort:

**Step 6 — Rollback recipe (DOCUMENT ONLY — execute only if Step 5 cannot be made green).**

**Rollback recipe:**

1. Identify the cutover commit hash (the commit that landed Task 1 + Task 2 Step 1-4 changes).
2. Revert it:
   ```
   git revert <cutover_commit_hash>
   ```
   This restores `main.py` (lifespan starts dispatcher_loop again), `routes/agent_messages.py` (no start_workflow call), `services/inapp_dispatcher.py` (`_handle_row` + `dispatcher_loop` come back), and `services/inapp_messages_store.py` (insert_pending without idempotency_key kwarg, no set_workflow_id helper).

3. **Temporal-side cleanup AFTER revert:**
   - The `workflow_id` column on inapp_messages is NULL for any row created by the asyncpg path post-revert — that is harmless. The column lives on (Plan 05 migration) but reverting Phase 28 code does NOT require running `alembic downgrade`.
   - Pending workflows started during the cutover window must be terminated so they don't conflict with the asyncpg path picking the same rows back up:
     ```
     temporal workflow terminate \
       --query 'WorkflowType="DispatchMessageWorkflow" AND ExecutionStatus=Running' \
       --reason "phase28 rollback"
     ```
     (Run from a host that can reach `localhost:7233` — i.e. with the `deploy/docker-compose.local.yml` overlay so 7233 is host-published, OR `docker exec deploy-temporal-1 temporal workflow terminate ...`.)
   - Stale `inapp_messages` rows that the workflow had partially advanced (e.g. status='forwarded' from forward_to_agent but no mark_message_done) are picked up by the legacy reaper at the next 11-minute cycle.

4. **Post-revert verification:**
   - `make dev-api-local` → stack boots; `curl /healthz` 200.
   - Send a curl message; verify api_server logs show `inapp-dispatcher` task active and the legacy `_handle_row` path is taken (NO `phase28.start_workflow` log lines).
   - Reply lands in `inapp_messages.bot_response` via the legacy path.

5. **Record revert in SUMMARY:** if rollback was executed, append to 28-06-SUMMARY.md:
   ```
   ## Rollback executed
   - Revert commit hash: <hash>
   - Reason: <one-line summary of why the forward fix failed>
   - Pending workflows terminated: <count>
   - Reaper-swept rows post-revert: <count from next reaper cycle, captured ~12 min later>
   ```

This rollback recipe is intentionally written down NOW (during planning) so the procedure is unambiguous if invoked under time pressure. Cutover plans without a written-down rollback are one-way doors; this is not.
