**Step 5 — Bullseye verification (container_not_ready window):**

Per CONTEXT.md `<specifics>` "The `container_not_ready` retry is the bullseye": validate the [250ms, 500ms, 1s, 2s, 4s] readiness retry budget covers the typical container-boot window.

Procedure:
1. Stop one of the agent containers: `docker stop <agent-container-id>`
2. Send a message to that agent via curl (mobile or curl recipe). The route handler will start the workflow.
3. Restart the container: `docker start <agent-container-id>` — within 5-10s of the message arrival.
4. Watch the temporal-worker logs: `docker compose ... logs -f temporal-worker`. Expect to see `phase28.check_container_ready.attempt` lines with attempt=1, 2, 3 (or however many attempts before success). Then `phase28.forward_to_agent.attempt` with attempt=1.
5. Verify the message reaches `bot_response` populated in the DB.
6. Visit Temporal UI for the workflow ID — expect COMPLETED status with the readiness retry visible in the activity history.

If the workflow times out (the 5-attempt budget exhausts before container_status='running'), document the actual time-to-ready observed; it should be << 7 seconds (the cumulative retry budget). If it's >>7s, the budget needs widening — but that's a Plan-09 finding, not a re-plan trigger; capture and flag for follow-up.
