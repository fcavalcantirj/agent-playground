Goal: empirically close RESEARCH §7 Risk 6 by demonstrating that a Python process running inside a container attached to `deploy_default` can issue an `httpx.get` to an agent-equivalent container's bridge IP and receive a 200 response.

The spike is structured as a docker-compose-driven integration:

1. Compose project `phase28spike-c`. Two services:
   - `bridge-target`: a tiny `nginx:alpine` container on `deploy_default`-equivalent network (named `phase28spike-c_default` — compose picks the project default). Serves a static `/healthz` returning 200.
   - `worker-probe`: built FROM the existing `tools/Dockerfile.api` image (same image the api_server uses), command is a one-shot `python -c "import httpx, docker, json, sys; ..."` script that:
     a. Uses `docker.from_env()` to look up `bridge-target`'s `NetworkSettings.Networks[<project_default>].IPAddress`.
     b. Issues `httpx.get(f'http://{ip}/healthz', timeout=5.0)`.
     c. Asserts `resp.status_code == 200` AND the network IP is in the 172.x or 10.x private range.
     d. Prints JSON `{"ok": true, "ip": ip, "status": resp.status_code}` to stdout and exits 0.
   - Worker probe mounts `/var/run/docker.sock:/var/run/docker.sock` (same as `temporal-worker` will).

2. The pytest test runs `docker compose -f <tmpfile> up --abort-on-container-exit worker-probe`, captures stdout, parses the JSON, asserts `ok == true` and `status == 200`. Tear-down runs `docker compose down -v`.
